# Workflows

Recurring patterns for how to make a certain kind of change in this repo.

## Wrapping shadcn/ui components instead of editing them

`src/components/ui/` is generated by the shadcn CLI and is **read-only** — never hand-edit it (see `CLAUDE.md`). But
these components often need project-specific behavior (RTL-aware positioning, brand colors, fixed sizing, a
non-default variant baked in). Don't reach for a one-off `className` override at every call site, and don't patch the
vendor file.

Instead: build **one** wrapper in `src/components/shared/` that is the *sole* consumer of that `ui/` component's
primitives, and drive every difference through props. Every other file in the app imports the wrapper, never the raw
`ui/` component.

**Why:** a shadcn upgrade (`npx shadcn add <name> --overwrite`) can safely re-pull the vendor file to pristine
upstream at any time without clobbering project customizations, because none live there. And a fix or design tweak
lands in exactly one place instead of being copy-pasted (and drifting) across every call site.

### Recipe

1. Identify the shared shape across call sites — what's the skeleton, what varies (title, icon, size, alignment,
   whether a close button shows, etc.).
2. Create `src/components/shared/<Thing>.tsx` that imports directly from `@/components/ui/<thing>` and composes it.
   Expose the variance as typed props with sensible defaults, not as free-form `className` escape hatches.
3. Update every call site to import the wrapper instead of the `ui/` primitives. Grep to confirm nothing outside the
   wrapper still imports the raw `ui/` component:
   ```
   grep -rln "from '@/components/ui/<thing>'" src --include="*.tsx" | grep -v "<Thing>.tsx"
   ```
   should return nothing (except other legitimate low-level composition, e.g. `Button` wraps `ui/button`).
4. If the vendor file itself was hand-edited at some point (drift), reset it to pristine via
   `npx shadcn add <name> --overwrite --yes`, then re-verify the wrapper still produces the desired look — the fix
   should live entirely in the wrapper now.
   - Known CLI quirk: the regenerated file may import `cn` from a package literally named `"cn"` instead of
     `@/lib/utils`. Fix that import path after every `shadcn add`.
5. Run `npm run typecheck && npm run lint:check && npm test` before considering it done.

### Worked examples in this repo

- **`AppDialog`** (`src/components/shared/AppDialog.tsx`) wraps `Dialog`/`DialogContent`/`DialogHeader`/`DialogTitle`/
  `DialogClose`/`DialogFooter` from `ui/dialog`. Props: `title`, `description`, `icon`, `align` ('start' | 'center'),
  `footer`, `children`, `contentClassName`, `showCloseButton`. Fixed a systemic RTL bug (hardcoded `text-left`/
  `right-4` in the shadcn defaults) in one place instead of overriding it at each of 7 call sites.
- **`Button`** (`src/components/shared/Button.tsx`) wraps `ui/button` to add `cursor-pointer shadow-button
  active:scale-[.985]` app-wide.
- **`LtrInput`** (`src/components/shared/LtrInput.tsx`) wraps `ui/input` to bake in `dir="ltr"` + `text-left` for
  Latin-script fields (email, verification codes) inside the otherwise-RTL app — was copy-pasted across 5 auth forms
  before being extracted.
- **`Toggle`** (`src/components/shared/Toggle.tsx`) wraps `ui/switch` instead of a hand-rolled `<button role="switch">`,
  recoloring the checked state to the app's green via a className prop rather than editing the vendor file.

### twMerge and custom theme tokens — a related gotcha

If a wrapper's default className and a call site's override both use **custom** Tailwind theme tokens (e.g.
`shadow-button` vs `shadow-chip`, both defined via `@theme` in `globals.css`), `cn()`'s `tailwind-merge` won't
dedupe them unless it's taught to — by default it only recognizes Tailwind's built-in utility names, not project-defined
ones. Two custom classes in the same conflict group can silently both end up in the DOM, with the winner decided by
arbitrary stylesheet order instead of your intent.

Fix at the source (`src/lib/utils.ts`): extend `tailwind-merge` with the custom class group once, e.g.

```ts
const customTwMerge = extendTailwindMerge({
    extend: {
        classGroups: {
            shadow: [{ shadow: ['card', 'button', 'button-ember', 'sheet', 'chip'] }]
        }
    }
})
```

Never work around this with a hardcoded arbitrary-value class (`shadow-[...]`) at a call site — that's exactly the
kind of literal, un-tokenized CSS the design system rules forbid. Extend the merge config instead.
